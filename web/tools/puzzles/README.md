# 4구 퍼즐 생성기

```sh
node web/tools/puzzles/make.js                         # 씨앗 20261101, 8단계 × 10개
node web/tools/puzzles/make.js --seed 20261101 --stage 7 # 바리케이드만 생성, 기존 70개 보존
node web/tools/puzzles/audit.js                        # 저장된 결과를 독립적으로 재검증
```

Node 내장 모듈만 사용한다. 단계는 0~7이며 `--stage 0,1`도 가능하다. 생성은 선택한 단계마다 작업자 스레드 하나에서 진행되며, 수 분 이상 걸릴 수 있다. 씨앗, 단계, 소스 버전이 같으면 좌표·답·난이도·순서가 같다. 실행 시간과 스레드 출력 순서는 결과에 영향을 주지 않는다. 앱에서는 생성기를 실행하지 않는다.

## 배치와 탐색

- `engine.js`: 앱/서버와 같은 `web/physics.js`, `web/game.js`를 직접 호출한다. 물리나 판정 사본은 없다.
- `layouts.js`: 씨앗 난수로 기술별 배치를 제안하고, 천 밖·공 겹침·비슷한 배치를 제외한다. 바리케이드 단계도 이 함수의 가까운 공 배치를 재사용한다. 공 좌표와 막대 배치는 분리한다.
- `walls.js`: 1~3개 막대를 따로 제안한다. 길이 0.15~0.5m, 두께 0.03m, 높이 0.04m. 회전한 사각형의 모서리와 실제 면 사이 거리로 공 겹침, 쿠션에서 공 지름 이상 간격, 막대 사이 공 지름 이상 간격을 검사한다.
- `search.js`: 두 빨간 공의 충돌 가능 각도, 쿠션 및 막대 면에 반사된 목표점의 각도, 여러 세기·당점을 훑는다. 성공하면 방향 ±0.3°와 세기 ±2.5% 주변을 더 세밀하게 비교한다. 탐색은 유한하며 모든 가능한 샷을 찾는 최적화는 아니다.
- `stage.js`: 후보를 검증하고 성공 폭이 넓은 순서로 정렬한다. 단계별 제안 상한 3,000개를 넘으면 실패한다. 목표 수에 못 미친 목록을 저장하지 않는다.
- `make.js`: 결과 전체를 검증한 뒤 `web/puzzles.js`의 `list`만 바꾼다. 선택하지 않은 단계와 `STAGES`는 보존한다. 진행 상황은 한 줄씩 출력한다.

성공 폭은 **저장되는 반올림된 샷** 주위 방향 ±0.5°, 속도 ±5%의 21×21 격자(441개)를 실제로 쳐서 측정한다. 당점·큐 각도는 그 답의 값으로 고정한다. 1% 미만이나 90% 초과인 후보는 버린다. 슬라이더 범위 밖의 시도는 실패로 센다. 이 수치는 이 격자에서의 조작 허용 폭이며, 초보자의 체감 난이도나 가능한 모든 답의 수를 뜻하지 않는다. 단계 안의 `n`은 이 성공률 내림차순이다.

모든 답은 세기 `g.vOf(0)`~`g.vOf(1)`, 당점 반경 0.8 이내이다. 저장된 속도와 `g.vOf(g.powerOf(V))`를 각각 재생한다. 기존 테스트와 같은 30초 재생과 서버의 40초 재생을 모두 검사하고, 공이 실제로 정지했는지도 확인한다. 막대가 있는 답은 앱·서버처럼 `w.walls = P.walls(z.walls)`를 설정한 상태로 재생한다. 규칙과 물리를 바꾸지 않는다.

## 기술 필요성 검사

| 단계 | 추가 검사 |
|---|---|
| 0 첫 득점 | 쿠션 없는 답부터 찾음. 최종 답도 쿠션을 거치지 않는지 audit에서 확인 |
| 1 모아치기 | 게임의 gather 판정(세 공 간 최대 거리 0.42m)을 그대로 사용 |
| 2 빈쿠션 | 게임의 bank 판정(첫 공보다 쿠션을 먼저)을 그대로 사용 |
| 3 밀어치기·끌어치기 | 빨간 공을 수구 양쪽에 제안. 무회전으로 양쪽 빨간 공의 충돌각 원뿔을 각 81개 방향, 전 방향 1° 격자, 세기 0~100%를 5% 간격으로 검사. 하나라도 풀리면 제외. 현재 목록은 끌어치기에 집중 |
| 4 상대 공 회피 | 노란 공이 없으면 성공 폭 50% 이상인 일반 샷을 먼저 찾고, 노란 공을 다시 놓으면 그 답이 실패해야 함. 다른 실제 득점 샷이 있어야 채택. 검사에 쓴 원래 답은 report의 open에 기록 |
| 5 돌려치기 | 게임의 three 판정(두 번째 목적구 전 쿠션 3번)을 그대로 사용 |
| 6 맛세이·점프 | 두 빨간 공의 충돌 가능 각도 전체가 더 가까운 노란 공의 충돌 가능 각도 안에 있어야 함. 평평한 샷은 첫 빨간 공에 가기 전에 노란 공을 만난다. el=0인 답 주변도 재생하여 실패 확인. 실제 올린 큐의 답은 direct 판정을 통과 |
| 7 바리케이드 | 막대 없이 무회전 샷의 성공 폭이 50% 이상인지 441개로 측정한다. 같은 샷이 막대에 닿아 실패해야 하며, 막대가 있는 새 정답은 쿠션 또는 막대 접촉을 포함한다. 새 정답도 441개로 1~90% 성공 폭을 확인한다. |

3단계의 무회전 검사는 유한 탐색이므로 수학적인 불가능성 증명은 아니다. 6단계의 차폐 검사는 평평한 직선 접근 전체를 검사한다. 두 단계 모두 최종 답을 별도로 다시 재생한다. audit는 목록과 보고서가 달라지거나 우회 답을 찾으면 실패한다.

## 결과, 번호, 재생성

- `report.json`: 단계별 씨앗, 물리·규칙 SHA-256, 성공 시도 수/441, 제안 번호, 회피·바리케이드 단계의 비교 답. 바리케이드는 openGood/openTotal/openPercent, 막대 수, 비교 샷과 정답의 막대/쿠션 접촉 수도 기록한다.
- `ids.json`: 번호와 배치 지문의 영구 이력. 현재 목록의 같은 배치는 같은 id를 쓴다. 목록에서 빠진 번호는 같은 배치를 다시 만들 때도 재사용하지 않는다. 다른 씨앗으로 새 배치를 만들면 그 단계에서 지금까지 쓴 가장 큰 id 다음 번호를 쓴다. 지운 배치의 항목도 **절대 지우지 않는다**. 바리케이드의 지문은 공뿐 아니라 막대 위치·크기·각도·높이까지 포함한다. 벽이 없는 기존 70개의 지문은 그대로 유지한다. 한 단계의 99개 번호를 소진하면 재사용하지 않고 실패한다.
- `.work/`: 중간 단계 결과. 저장소에는 넣지 않으며 재실행은 처음부터 시작한다.

다른 씨앗으로 재생성하면 선택한 단계의 목록을 교체한다. 기존에 푼 퍼즐의 서버 보상 기록은 예전 id로 남는다. 공개한 퍼즐의 id나 좌표를 손으로 고치지 말고 생성기와 이력을 함께 커밋한다.

701~710은 이미 6단계(맛세이·점프)에서 사용 중이다. 새 7단계는 기존 단계별 100단위 규칙을 유지하여 801~810을 사용한다. 기존 번호를 재배정하지 않는다.

`--stage 7`은 기존 0~6단계 목록과 보고서·ID 이력을 보존한다. `--stage all` 또는 옵션을 생략하면 전체 단계를 생성하므로, 바리케이드만 추가할 때는 반드시 `--stage 7`을 쓴다.

## 최종 확인

```sh
node web/tools/puzzles/test-walls.js
node web/tools/puzzles/audit.js
node web/test/run.js
sh web/build.sh
node web/tools/check.js
node web/test/browser/smoke.js
```

브라우저 검사는 Playwright와 Chromium이 필요하다. 실기기 손맛·소리·속도는 확인 못 함. 자동 검사의 실제 결과와 브라우저 실행 가능 여부는 PR에 기록한다.
