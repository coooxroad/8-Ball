# Claude에게 — CUE 인게임 프레임 저하 진단 및 최적화 요청

작성: Codex · 요청일: 2026-11-02 (KST)
분석 기준: `main@558c30499b2b241b350f2d501107d2c4f2f7a9aa`

Claude, 사용자가 모바일 인게임에서 렉을 경험하고 있다. Codex가 현재 소스를 읽고 일부 CPU 계산과 도형 수를 확인했다. 아래 근거를 출발점으로 **원인을 측정하고, 효과가 확인되는 최적화를 작은 변경으로 구현해 달라.** 이 PR은 요청서만 추가한다. 구현 완료나 실기기 개선을 주장하는 PR이 아니다.

사용자의 핵심 요구는 원신·마인크래프트·와일드 리프트보다 작은 장면인 당구게임에서 왜 끊기는지 밝히고, 현재 게임의 물리·조작성·디자인을 보존하며 개선하는 것이다. 다른 게임의 내부 구현을 확인한 것은 아니며, 게임 간 그래픽 복잡도 비교만으로 원인을 확정하지 않는다.

## 1. 목표와 보존 조건

- 우선 목표는 대상 모바일 기기에서 안정적인 60fps와 즉각적인 조작 반응이다. 현재 60fps 이상 나오는 기기를 일괄 제한하지 말고, 고주사율에서는 성능·발열과 함께 판단한다.
- 실제 샷의 `TICK = 1 / 120`, 물리 상수, 충돌 정확도, 동시 충돌 처리, 맛세이·점프, 규칙을 유지한다. 틱을 줄이거나 공을 강제로 멈추는 방법으로 숫자만 높이지 않는다.
- 조준선과 실제 샷은 같은 물리 엔진·같은 입력을 사용한다. 각도·세기·스핀을 거칠게 반올림하거나 다른 간이 물리로 바꾸지 않는다.
- 서버 검증·온라인 동기화·리플레이가 같은 결과를 낼 수 있어야 한다. 로컬 최적화로 서버와 다른 궤적을 만들지 않는다.
- 글꼴·탭·버튼의 선명도를 유지한다. 성능 때문에 앱 전체의 DPR/CSS 배율을 낮추지 않는다. 3D 내부 해상도와 DOM UI 해상도를 구분한다.
- 알감자의 울퉁불퉁한 실루엣, 볼링공 구멍, 공 종류 구분, 큐·테이블·트레일의 개성을 보존한다.
- AI 난이도·성격·플레이스타일·계획된 연출을 임의로 단순화하지 않는다.
- 상점·장착·보상·저장·친구 경기·랭킹전·훈련·퍼즐·하이라이트의 기존 동작을 보존한다.
- `AGENTS.md`를 먼저 읽고 파일별 책임과 빌드의 공유 범위를 지킨다. 관련 없는 구조 재작성, 엔진 교체, 릴리스/서명 workflow 변경은 이번 작업 범위가 아니다.

## 2. 먼저 증상을 나눠서 계측

아직 **사용자 실기기에서 GPU/CPU 프레임 시간을 측정하지 않았다.** 따라서 아래 그래픽 항목은 코드상 비용 후보이며, 지속적인 프레임 저하의 주범으로 확정한 것이 아니다.

다음 경우를 동일 배치·동일 샷으로 분리한다.

| 상황 | 분리해서 볼 항목 |
|---|---|
| 가만히 있는 조준 화면 | 불필요한 렌더·DOM 갱신·효과 루프 |
| 조준/세기/스핀을 계속 드래그 | preview 계산, 입력 지연, 레이아웃, 조준선 업로드 |
| 8볼 브레이크 | 실제 물리, 다중 충돌, 음성/충돌음 폭주, GPU |
| 공이 굴러가는 동안 | 지속적인 CPU/GPU 비용, 트레일, 해상도 |
| AI가 샷을 선택하는 순간 | 메인 스레드 long task |
| AI가 큐를 움직이는 동안 | 매번 달라지는 조준선의 재시뮬레이션 |
| 탑뷰 / 고정 3D / 회전 중 / 플레이어 시점 | static 캐시 재사용, depth 패스, 카메라 |
| 기본/감자/볼링/만화/미러 공 | 도형, 셰이더, 텍스처, 효과 |
| 기본/물 테이블, 트레일 없음/분필/불/물보라 등 | 픽셀 비용·버퍼 업로드·효과 메모리 |
| 게임 진입 직후 / 5~10분 플레이 후 | 셰이더·텍스처 첫 사용, 메모리, 발열 |
| Chrome 웹 / Android WebView APK | 같은 커밋·같은 설정·실제 GPU 가속 여부 |

계측은 개발 모드에서 가볍게 켜고 끌 수 있게 한다. 프레임마다 console 출력이나 전체 로그 직렬화를 하지 않는다.

- 평균 FPS 외에 **raw rAF 간격의 p50/p95/p99/최댓값**, 16.7/33.3/50ms를 넘은 간격 수, 최장 메인 스레드 작업을 기록한다. 주사율·프레젠테이션 간격을 고려해 해석한다.
- `app/90-loop.js:frame`은 dt를 0.1초로 제한하고, FPS도 그 제한된 dt로 나눈다. 100ms보다 긴 지연이 축소 표시될 수 있으므로 **측정용 raw 시간과 게임 진행용 dt를 분리**한다. rAF 호출 수와 실제 그린 프레임 수도 구분한다.
- CPU: `autoTick/aiPlan`, `P.preview`, `P.step`, `aheadStep`, `scene.frame`, DOM/style/layout, GC를 나눠 본다.
- GPU: 렌더 해상도, MSAA, 렌더 패스별 draw calls·triangles, 효과 유무를 기록한다. Three.js r128의 `renderer.info`는 render 호출별로 초기화되므로, **배경/depth/동적 패스를 합산**해서 보고한다. 측정 때문에 stats 설정이 제품 동작을 바꾸지 않도록 한다.
- `renderer.render()` 호출의 CPU 소요 시간만 GPU 시간이라고 쓰지 않는다. 가능하면 지원되는 GPU timer query를 비동기로 사용하고, 불가능하면 해상도·효과·패스 A/B로 판단한다. `gl.finish` 같은 강제 동기화를 상시 계측에 넣지 않는다.
- 데스크톱 CPU throttling과 SwiftShader는 비교 실험 수단이다. 실기기 GPU 성능 또는 사용자 기기의 FPS로 환산하지 않는다.
- 장면 정지로 렌더를 생략한 것은 정상이다. 정지 화면의 draw 수를 인위적으로 늘려 FPS 수치를 높이지 않는다.

## 3. 확인된 구조적 문제 — 먼저 처리할 것

### A. AI의 동기 샷 탐색을 화면 스레드에서 분리

위치:
- `web/app/40-shot.js:autoTick`
- `web/app/50-match.js:match.auto`
- `web/app/54-ranked.js:ranked.auto`
- `web/app/30-home.js:homeDemo.auto`
- `web/ai/00-kit.js:simShot`, `10-pool.js`, `20-carom.js`, `50-human.js:humanPlan`

현재 `a.src.plan()` → `game.aiPlan()`이 프레임 함수 안에서 동기 실행된다. 후보마다 `P.run(copy, 20)` 등으로 샷을 끝까지 탐색한다. 생각하는 시간인 `think`를 먼저 기다려도, 실제 탐색이 시작되면 메인 스레드가 그대로 막힌다.

Codex의 분석 환경에서 같은 초기 배치를 3번 실행한 Node 간이 측정 중앙값은 일반 4구 AI 약 84ms, 최고 난이도 8볼 AI 약 172ms였다. 이 값은 한 머신·소수 표본·표준 AI 경로의 참고값이며, 모바일 측정값이나 최악값이 아니다. 사람 같은 대역 AI도 일부 표본에서 16.7ms를 넘었다. 대표 배치를 더 넓게 측정해 달라.

요청:
- 지속해서 재사용하는 Web Worker에서 **기존 AI와 물리 코드**로 탐색한다. WebView 오프라인 번들과 웹 배포 모두 작동해야 한다.
- 화면에는 생각 중 표시와 입력 반응을 유지하고, 결과가 준비되면 기존 계획 연출로 연결한다.
- 경기/차례/world revision/요청 번호를 붙여 재시작·홈 이동·타임아웃·새 경기 뒤의 오래된 응답을 버린다. 무제한 작업 큐를 만들지 않는다.
- 현재 AI 수준과 persona, 규칙 문맥, seed/random 사용, 장비, `preShot` 등 필요한 데이터를 빠짐없이 전달한다. 스냅샷의 가변 참조를 공유하지 않는다.
- Worker를 쓰기 어려운 환경의 fallback은 실제로 나눠 실행되는 탐색이어야 한다. 큰 동기 함수를 `setTimeout`으로 감싸는 것만으로 해결했다고 하지 않는다.
- AI 계획 지연이 온라인 샷 시간·재접속·기권 처리와 충돌하지 않는지 확인한다.
- 초기 Worker 준비/직렬화 비용도 측정한다. 실제 공의 이동 전체를 Worker로 옮기는 대공사부터 할 필요는 없다.

### B. 조준선 계산의 지연과 중복 작업

위치: `web/scene/90-frame.js`의 guideKey/`P.preview`, `web/physics.js:preview`, `web/scene/50-guide.js:ribbon`

guideKey가 바뀔 때마다 실제 물리를 동기로 돌린다. 긴 선에서는 충돌 후 최대 15초를 추적하고, 루프 상한에는 그 이전 경로 시간도 포함된다. 가만히 있을 때 key 캐시는 이미 있으므로 “캐시를 새로 넣으면 해결”이라고 쓰지 않는다.

요청:
- 먼저 짧게/보통/길게/전부와 8볼/캐롬의 계산 시간을 분리한다. 짧은 선은 긴 선보다 싸므로 동일 비용으로 가정하지 않는다.
- 입력 반영과 큐 움직임을 우선하고, 비싼 preview는 Worker 또는 제한된 작업 단위로 분리한다.
- 최신 입력만 대기시키고 이전 계산 결과는 요청 번호로 폐기한다. 입력이 빠르게 바뀔 때 오래된 경로를 현재 경로로 확정 표시하지 않는다. 드래그가 멈추면 최신 입력의 정확한 결과로 수렴한다.
- 계산 빈도 조절은 입력 정밀도 저하와 다르다. 실제 샷 입력과 물리 스텝을 반올림하지 않는다.
- AI와 preview를 하나의 Worker에 넣을 경우 긴 AI 작업이 사용자 preview를 막지 않도록 역할/우선순위/취소를 설계한다.
- 매 계산의 clone·경로 배열 생성·ribbon 채움·GPU 업로드도 나눠 측정하고, 필요한 경우 재사용 버퍼를 사용한다.

### C. FPS 표시를 개선 검증에 쓸 수 있게 수정

위치: `web/app/90-loop.js:frame`

앞서 설명한 raw dt 분리를 적용한다. 계측은 게임 진행용 accumulator/샷 타이머의 정책을 임의로 바꾸지 않아야 한다. 오랫동안 백그라운드에 있던 시간을 억지로 따라잡는 무제한 루프도 만들지 않는다. 느린 프레임·탭 복귀·온라인 시계 정책을 각각 검증한다.

## 4. 지속적인 렌더 비용 — 실제 기기 A/B로 우선순위 결정

### D. 공 그림자를 한꺼번에 그리기

위치: `web/scene/30-balls.js:ballSet`, `web/scene/90-frame.js`의 공/그림자 갱신

공 하나당 접촉 그림자 1개와 램프 그림자 3개가 별도 Mesh다. 공 16개가 활성화된 8볼에는 그림자 평면이 64개 있다. Mesh/재질 공유만으로 draw call이 자동으로 합쳐지는 것은 아니다.

- 동일 재질의 평면을 `InstancedMesh` 또는 배칭한 버퍼로 묶는 방안을 비교한다.
- 4개의 그림자를 시각적으로 보존하고, 동일 재질 그룹끼리 배칭하는 방법부터 검토한다.
- 투명 블렌딩·깊이·renderOrder·뜨는 공의 오프셋·포켓 빠짐/테이블 밖 공/캐롬 반지름 차이를 보존한다.
- 공 자체의 instancing은 번호/띠/서로 다른 텍스처 처리 비용이 있으므로 그림자부터 시행한다.

### E. 공의 화면 크기에 맞춘 LOD

위치: `web/scene/30-balls.js:sphere/geomOf/dressBall`

현재 코드와 번들 Three.js r128의 SphereGeometry index로 확인한 수치:

| 세트 | 도형 분할 | 공 하나의 삼각형 | 16개일 때 |
|---|---:|---:|---:|
| 기본 | 40 × 28 | 2,160 | 34,560 |
| 알감자 | 64 × 48 | 6,016 | 96,256 |
| 볼링공 | 128 × 96 | 24,320 | 389,120 |

- 화면에 투영된 공 지름을 기준으로 작은 경기 공/확대 3D/상점 프리뷰의 세부 수준을 구분한다.
- 낮은 단계의 실루엣과 구멍을 보존하고 가까운 시점에서는 현재 정밀도를 유지한다.
- 도형은 세트/LOD별로 캐시하고 공유한다. 매 프레임 생성하거나 LOD 경계에서 계속 교체하지 않는다. 전환 히스테리시스를 둔다.
- normal/bump map으로 대체할 수 있는 미세 표면과 실루엣에 필요한 기하를 구분한다.
- 모든 공의 재질을 무조건 저품질로 바꾸거나 볼링/감자 스킨을 끄는 방법으로 끝내지 않는다.

### F. 3D 시점의 테이블 depth 패스와 static 재렌더

위치: `web/scene/90-frame.js`의 orbit.live/staticDirty/depthMat, `web/scene/60-view.js:applyCamera`, `web/app/70-buttons.js:eyeTick`

카메라가 움직일 때는 static 배경을 직접 그리고, 고정되면 캐시한다. 고정 3D에서도 가림 처리를 위해 sScene 전체를 depth material로 다시 그린다. 포켓에 공이 빠질 때 탑뷰에서도 depth 패스가 생긴다.

- depth 전용의 단순화된 occluder를 만들거나 관련 레이어/보이는 부품만 그리는 방법을 비교한다.
- 테이블 전체를 다시 그려야 하는지, 포켓 입구/쿠션/레일 등 필요한 가림 형상만으로 충분한지 확인한다.
- 포켓 공이 레일 앞에 튀어나오거나 낮은 시점에서 뒤쪽 공이 비치는 회귀를 막는다.
- 카메라가 고정됐을 때 불필요한 staticDirty가 반복되지 않는지 카운터로 확인한다.
- 움직이지 않는 부품은 재질별 merge/행렬 갱신 생략을 검토하되, 테이블·스킨·조명 변경 시 갱신 경로를 보존한다.

### G. 실제 성능에 반응하는 3D 해상도 정책

위치: `web/scene/60-view.js:resize/setQuality`

현재 auto는 성능 측정 없이 화면 크기/DPR로만 정한다. 일반 인게임의 예산은 auto 4.2M, high 9M, low 1.6M pixels다. `Math.max(1, ...)` 하한 때문에 CSS 화면 자체가 예산보다 큰 경우 **엄격한 상한이 아니다.** 홈 tilt에는 별도 예산이 있다.

- 먼저 CPU/GPU 병목을 구분한다. CPU로 막힌 프레임에 해상도만 계속 낮추지 않는다.
- 충분한 시간 창과 히스테리시스를 가진 renderScale을 검토한다. 프레임마다 render target을 재생성하지 않는다.
- DOM 글씨/컨트롤 해상도, 좌표 변환, 터치 hit test, 화면 회전, projection을 유지한다.
- 이전 PC 홈의 흐린 글씨·기울어진 캔버스 문제를 되살리지 않는다. 인게임 정책을 홈 tilt의 선명도 정책에 무차별 적용하지 않는다.
- 지원 GPU 크기 제한, context loss/restoration, 수동 low/high 옵션과 충돌하지 않도록 한다.
- 고주사율에서 렌더가 90/120회 호출되는 비용도 측정한다. 렌더 주기와 120Hz 물리 틱은 별개다. 60fps 절전 옵션은 근거가 있을 때 제시한다.

### H. MSAA·캐시·그림자맵의 비용을 정확히 분류

위치: `web/scene/00-setup.js`, `web/scene/10-room.js`, `web/scene/60-view.js:resize`

- 기본 컨텍스트가 MSAA를 요청하고 WebGL2의 static 캐시에 multisample render target을 쓴다. 저사양 프로필에서 효과/메모리/재베이크 비용을 비교한다. 두 개가 있다는 사실만으로 매 프레임 같은 장면을 두 번 AA한다고 설명하지 않는다.
- 2048² 그림자맵 3개가 있지만 `shadowMap.autoUpdate=false`다. **실시간으로 매 프레임 그림자를 굽는 구조로 오해하지 않는다.** 갱신 이유·횟수와 시점 전환 때의 스파이크를 확인한다.
- static 그림자 해상도는 실제 화면 크기에 비해 과한 경우에만 조정하고 품질을 비교한다.
- 이미 있는 static 배경 캐싱과 dirty 렌더 생략을 보존한다. 배경 캐싱을 처음부터 새로 구현하는 중복 작업을 하지 않는다.
- 정적인 장면도 RT 내부에서는 깊이 정렬이 필요하므로 depthBuffer를 무턱대고 끄지 않는다.

### I. 텍스처·셰이더의 첫 사용과 메모리

위치: `web/scene/30-balls.js:ballTexture/setBalls/ballPortrait`, `web/scene/40-cue.js:setCue`

- 공 텍스처가 각 1024×512이고 pool 16개와 carom 4개를 만든다. RGBA8 기준 20개는 기본 레벨만 약 40MiB, 전체 mip chain까지 약 53MiB다. 이는 도형이나 원본 WebP 용량과 다르며, 실제 GPU 포맷/보유 상태는 측정한다.
- 작은 화면 공에 필요한 texture LOD·해상도와 확대/상점의 해상도를 구분할 수 있는지 검토한다. 번호·색·띠를 읽을 수 있어야 한다.
- 장착·테이블·스킨을 반복 변경했을 때 geometry/texture/program 수가 계속 늘어나는지 검사한다. 정상 캐시와 실제 누수를 구분한다.
- 버려진 큐의 비동기 텍스처 콜백, 교체된 material/map, 재생성된 RT의 수명도 확인한다.
- 새 스킨의 첫 샷에서 셰이더 컴파일/texture upload가 몰리는지 확인하고, 필요하면 로딩/유휴 시점에 준비한다. r128에서 지원하지 않는 compileAsync API를 가정하지 않는다.
- 상점의 `ballPortrait`는 readRenderTargetPixels와 PNG 직렬화를 동기로 수행한다. 현재는 **상점 프리뷰 경로**이므로 이를 일반 인게임의 매 프레임 원인으로 적지 않는다. 첫 진입/전환 지연은 캐시·분할 생성으로 별도 개선할 수 있다.

## 5. 효과·입력·부가 작업 — 측정 후 적용할 추가 후보

### J. 트레일과 물 테이블

위치: `web/scene/55-chalk.js`, `56-fx.js`, `57-comic.js`, `20-table.js:waterTick`

- 분필은 수정될 때 1024×512 CanvasTexture를 업로드한다. 실기기에서 그 비용을 보고 업데이트 합치기/주기/표현을 조정한다. 물리 trace의 꺾임 위치는 보존한다.
- 입자 효과는 이미 Points 버퍼와 최대 개수 제한을 쓴다. 다시 “입자를 전부 Points로 바꾸자”는 중복 구현을 하지 않는다.
- 다만 fxStep은 활성 개수와 무관하게 attributes를 dirty 처리한다. active range, DynamicDrawUsage/updateRange, 빈 버퍼 조기 반환이 실제로 이득인지 비교한다.
- 물보라/물 테이블의 링은 최대 30개 별도 Mesh다. instancing 후보이며 투명 정렬을 확인한다.
- 미러볼 discoTick은 매 프레임 점 객체를 다시 채운다. 할당/GC가 보이면 풀·고정 배열로 재사용한다.
- 물 셰이더는 화면의 넓은 부분에서 sin/cos 기반 루프를 실행한다. 해상도/효과 단계별 GPU 비용을 측정한다. 물의 움직임과 구매한 효과를 일괄 제거하지 않는다.
- 물의 시간 갱신은 30Hz 지향이지만 공이 움직여 다른 이유로 그리는 프레임에서는 더 자주 표시될 수 있다. return false만으로 물 전체의 비용이 정확히 30fps로 제한됐다고 가정하지 않는다.
- 메뉴에 가려졌거나 탭이 숨겨진 상태에서 무의미한 효과·렌더를 계속하는지 확인한다. 온라인 경기의 상태 진행과 시각 효과의 정지는 구분한다.

### K. 입력 이벤트·DOM 작업 합치기

위치: `web/app/80-input.js`, `web/app/10-ui.js:setPowerUI`, `web/app/50-match.js:shotClock`

- pointermove에서 스타일 쓰기, clientWidth/clientHeight/getBoundingClientRect 읽기, Canvas 다이얼 그리기가 섞인다. Performance trace에서 forced layout/paint 여부를 확인한다.
- 크기는 resize/layout 때 캐시하고, 입력의 현재 상태를 모아 프레임당 한 번 UI를 갱신하는 방안을 검토한다.
- 다이얼처럼 상대 이동량이 중요한 조작은 이벤트를 버리지 말고 delta를 합산한다. pointerup 직전 마지막 세기/스핀은 실제 샷에 반드시 반영한다.
- setPowerUI가 같은 표시값을 계속 쓰지 않도록 하되, 세기 입력 자체는 유지한다.
- 다이얼의 정적인 그라데이션/프레임은 캐시하고, 움직이는 부분만 그릴 수 있는지 비교한다.
- 샷 시계의 숫자는 이미 초가 바뀔 때만 갱신한다. 시간 바의 CSS 변수 갱신과 paint 비용만 분리한다. UI 전체 재설계는 하지 않는다.

### L. 빠른 진행용 선행 시뮬레이션

위치: `web/app/90-loop.js:aheadStart/aheadStep/stepSim`

fast 옵션을 켜면 실제 샷 외에 끝까지 내다보는 복사 시뮬레이션을 프레임마다 약 3ms 예산으로 실행한다. 모바일에서는 한 프레임 예산의 의미 있는 부분이다. 처음 최소 4스텝 조건이 있어 엄격한 3ms 상한도 아니다.

- fast on/off를 비교하고 남는 시간에 맞춘 예산 또는 Worker를 검토한다.
- 예측이 늦으면 현재처럼 정상 속도로 진행하고 결과가 준비된 후 전환한다. 예측 결과로 실제 물리 상태를 덮어쓰지 않는다.
- 두 배 진행에서 추가 실제 물리 틱·효과·소리도 함께 측정한다. 샷 결과나 마지막 공 접촉 시점 판단을 바꾸지 않는다.

### M. 물리의 할당 비용 — 증거가 있을 때만 좁게 수정

위치: `web/physics.js:contacts/collideGround/sub/step`

접촉 처리에는 배열·객체·Set·Map 생성과 반복 풀이가 있다. 특히 브레이크/동시 접촉에서 비용을 볼 필요가 있다. 그러나 공은 최대 16개이며, 일반적인 물리 두 틱은 Codex의 제한된 Node 표본에서 AI 탐색보다 훨씬 쌌다. 전체 물리를 첫 번째 주범으로 단정하지 않는다.

- 프로파일에서 보이면 scratch buffer/고정 배열 재사용, 안전한 조기 제외를 검토한다.
- 거리/접근 조건으로 거르는 경우 기존 경계·공중 충돌·동시 접촉을 보존한다.
- 반복 상한·수렴 오차를 낮추거나 충돌 쌍 순서를 바꾸는 방식은 이번 목표에 맞지 않는다.
- 공간 분할·WASM·엔진 재작성은 효과가 증명되지 않으면 미룬다. 구조를 복잡하게 만드는 것 자체는 최적화가 아니다.

### N. 소리·저장·리플레이·네트워크의 순간 비용

- `audio.js:hit`에는 이미 동시 voice 제한과 onended disconnect가 있다. 브레이크의 오디오 노드 생성·리버브 비용은 sound on/off로 측정한다. 충돌음 제한/중복 합치기를 하더라도 주요 충돌 타이밍은 유지한다.
- `app/90-loop.js:snapshot`은 경기 저장/하이라이트/로그를 동기 직렬화한다. 저장본이 커진 뒤 턴 시작/샷 경계의 지연과 중복 snapshot을 측정한다. 경기 복구·증거 로그를 누락하지 않도록 합치거나 시점을 조정한다.
- `highlights.record`는 plan을 위한 재시뮬레이션과 tape 생성을 수행한다. 결과 썸네일·재생 진입에서 반복되는지 확인하고 동일 샷 결과를 캐시/분할하는 방안을 검토한다. 이는 결과/리플레이 전환 지연이며 공 이동 중 렉과 구분한다.
- 랭킹 조준 전송은 이미 약 15Hz이며 값이 같으면 보내지 않는다. 불필요한 통신 최적화로 샷 패킷·재전송·상대 조준 보간을 손상시키지 않는다.
- 네트워크 지연과 로컬 프레임 저하를 각각 기록한다. 서버 요금/호스팅 변경으로 로컬 GPU·메인 스레드 렉을 해결하려 하지 않는다.

## 6. 구현 순서와 완료 기준

권장 순서:
1. 최소 계측과 재현용 고정 배치/샷을 마련한다.
2. AI 동기 블로킹을 분리하고, 원래 선택/연출이 유지되는지 확인한다.
3. 실기기 측정상 큰 항목부터 그림자 배칭, LOD, depth 패스, preview 분리, 입력 갱신 합치기를 선택한다.
4. 그래픽 부하가 남으면 동적 해상도/AA/효과 단계를 조절한다. 모든 화질을 먼저 낮추고 끝내지 않는다.
5. 이득이 없는 변경은 넣지 않고, 남은 후보는 근거와 함께 미룬다. 모든 후보를 한 커밋에 구현하지 않는다.

검증:
- 같은 기기·WebView/Chrome 버전·해상도·설정·샷을 사용한 전후 표를 남긴다. 평균 FPS만 쓰지 말고 p95/p99, 50ms 이상 지연, 입력 반응, draw calls, triangles, pixels, 메모리 추이를 함께 기록한다.
- Worker의 늦은 응답, 재시작/홈 이동/새 경기, 연속 입력, 시간 초과, 연결 복구를 검증한다.
- 같은 초기 상태·같은 샷으로 최종 위치, 충돌/포켓/득점·차례가 기존 엔진과 같음을 확인한다. 30/60/120Hz 렌더와 지연 프레임에서도 물리 틱 처리 결과를 검사한다.
- 탑뷰/고정 3D/회전/눈높이에서 공·레일·포켓 가림, 확대 LOD, 번호/띠, 감자 실루엣/볼링 구멍, 물/트레일의 스크린샷을 비교한다.
- 장착과 경기/홈 왕복 후 리소스 수가 계속 증가하지 않는지 확인한다.
- `node web/test/run.js`
- `sh web/build.sh`
- `node web/tools/check.js`
- `node web/test/browser/smoke.js`
- 해상도/좌표/context 경로를 바꾸면 `node web/test/browser/graphics.js`도 현재 기준과 맞춰 실행한다. 오래된 기대값이 있으면 이유를 밝히고 실제 보존 조건으로 검사한다.
- 공유 물리/프로토콜/직렬화에 영향이 있으면 서버 검사도 실행한다.
- 실기기에서 확인하지 못한 항목은 정확히 그렇게 적는다. 소프트웨어 렌더러나 Node 표본을 모바일 개선 수치로 쓰지 않는다.

완료 보고에는 **원인 / 적용한 변경 / 전후 수치 / 보존 확인 / 남은 문제**를 적어 달라. 60fps는 목표이며, 측정 없이 달성했다고 쓰지 않는다.

## 8. 이 요청서의 검증 범위

- 기준 커밋의 AI·물리·scene·app·스타일·Android wrapper를 읽고 코드 경로를 확인했다.

- 이 PR은 위 요청서 한 파일만 추가한다. 게임 코드·물리·제품 UI·배포 설정에는 변경이 없다.
